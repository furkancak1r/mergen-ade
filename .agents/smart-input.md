# OpenCode Smart Input Guidelines

## OpenCode Smart Input Guidelines
- **Smart Input is terminal-scoped and runtime-only**: Store Smart Input draft, queue, edit state, and auto-run state on the foreground terminal session, not on `ProjectRecord`. Multiple OpenCode foreground terminals in the same project must have isolated queues.
- **Smart Input visibility is narrow**: Render the Smart Input footer only for live `TerminalKind::Foreground` terminals owned by `AiCliTool::OpenCode` with `opencode_session_active == true`. Do not show it for background terminals, other AI CLIs, launch-pending OpenCode terminals, or preserved turn-complete state after the OpenCode process exits.
- **Two delivery modes are distinct**: `Steer Now` sends immediately to the terminal; `After Done` adds to Mergen's queue and waits for OpenCode completion. Do not route `After Done` tasks through OpenCode's own busy-turn queue.
- **Auto-run waits for real OpenCode completion**: Dispatch queued tasks only when OpenCode has `OpenCodeTransportStatus::Idle` and `OpenCodeAttentionReason::TurnComplete`. Do not auto-dispatch while OpenCode is `Working`, `Permission`, `QuestionAsked`, `PlanModePrompt`, or `SessionError`.
- **Auto-run sends exactly one task per completion**: After dispatching one queued task, the terminal state must transition back to Working and the next queued task must wait for the next turn-complete signal.
- **Paste-safe delivery is mandatory**: Smart Input sends must use `TerminalRuntime::capture_paste_bytes()` and `send_paste_bytes()`, followed by immediate Enter and confirmation Enters (count from `TerminalPromptSubmitOptions`). Attachment-only payloads must also send an immediate Enter and transition OpenCode to Working so the queue waits for completion.
- **Auto-run must not steal focus**: Automatic Smart Input dispatch must not call `set_active_terminal()` or otherwise change the active terminal. Manual `Send` / `Now` actions may activate the target terminal.
- **Smart Input text focus owns keyboard input only while visible**: Add Smart Input draft/edit IDs to extended text focus checks and focus surrender. When visible Smart Input is focused, terminal capture, terminal shortcuts, and AI attention stealing must not consume its text. Stale egui focus for hidden Smart Input fields must be ignored so terminal input resumes after OpenCode exits.
- **Smart Input must auto-claim keyboard focus when visible**: When a visible Smart Input draft is unfocused and no modal, popup, or other UI text input owns the keyboard, focus must automatically move to the active terminal's Smart Input draft. This happens at the start of `raw_input_hook()` before event routing, inside `set_active_terminal()` after clearing other UI focus, and after `draw_main_area()` each frame as a safety net. Edit/draft transitions must also restore the appropriate focus so typing continues uninterrupted. Auto-focus must never fall back to a different visible terminal's Smart Input when the active terminal does not have Smart Input.
- **Terminal output clicks suppress Smart Input auto-focus**: When the user clicks on the terminal output area (not the Smart Input footer), a `terminal_output_focus_override` is set for that terminal. `ensure_smart_input_focus()` respects this override and does not re-focus the Smart Input draft. `set_active_terminal()` also skips Smart Input re-focus when the override is active for the target terminal. This allows the user to type directly into the terminal PTY after clicking the output. The override is cleared when Smart Input is explicitly clicked/focused, when the active terminal switches to a different terminal, or when the terminal is closed.
- **Modal/popup open must surrender Smart Input focus**: When any modal, popup, context menu, or the Create Worktree popup is open, `ensure_smart_input_focus()` must actively surrender Smart Input focus (draft, edit, and question custom input) so that keyboard input goes to the modal's text fields rather than the Smart Input draft behind it.
- **Plain Enter submits, Ctrl+Enter inserts newline**: Capture plain Enter in `raw_input_hook()`, remove it from the event stream, and defer the actual Smart Input submit until after egui `TextEdit` processes same-frame text events.
- **Plain Tab is forwarded to the terminal while Smart Input keeps focus**: When the Smart Input draft or edit field has focus, pressing plain `Tab` sends `\t` to the terminal runtime directly and consumes the event so egui focus traversal does not move focus away. `Shift+Tab` remains blocked to prevent reverse focus traversal from leaving the Smart Input field.
- **Terminal navigation shortcuts remain active while Smart Input is focused**: `Ctrl+Arrow` and `Ctrl+Alt+Arrow` grid/filter/linear navigation shortcuts are still buffered for terminal switching even when the Smart Input draft or edit field owns keyboard focus. Plain `ArrowUp`/`ArrowDown` continue to navigate Smart Input history.
- **Primary paste shortcut inserts image attachments when clipboard contains an image**: When Smart Input draft or edit field is focused, pressing `Ctrl+V` (or `Cmd+V` on macOS) with an image-only clipboard must both (1) insert the image file path into the draft/edit text via `Event::Paste(path)` and (2) push a `SmartInputAttachment` into `draft_attachments` (or `edit_attachments`) so the chip renders in the UI. On submit, attachments are sent to the terminal first via bracketed paste so OpenCode can convert them into `[Image N]` inline attachments. Text-only paste still flows through the normal paste path.
- **Image attachments are first-class Smart Input objects**: Attachments travel with queued tasks, edits, and history navigation. They are not plain text fragments; removing an attachment from a task leaves the text unchanged, and vice versa.
- **Attachment submit order matches OpenCode's native paste flow**: When a Smart Input task containing both text and image attachments is dispatched, each attachment path is delivered as a separate bracketed-paste event to the terminal, followed by the text prompt. This ensures OpenCode's TUI `onPaste` handler recognises the image and creates a real `[Image N]` inline attachment.
- **Smart Input attachment delivery must not mutate terminal title or history buffers**: Attachment paths are transport payloads for OpenCode's image paste flow, not user prompt text. `deliver_smart_input_attachment_to_terminal()` must deliver bracketed paste bytes without calling `append_pending_line()` or `append_pending_input_for_history()`. `submit_smart_input_attachment_only()` must clear `pending_line_for_title` and `pending_input_for_history` after sending Enter so the attachment path is not recorded as terminal input.
- **Queue editing remains local and non-destructive**: Reorder, edit, delete, and send-now operations must mutate only the current terminal's Smart Input queue. Deleting or sending one task must not affect foreground saved messages or other terminals.
- **Footer height must fit all visible rows without clipping**: `SMART_INPUT_BASE_FOOTER_HEIGHT` and `SMART_INPUT_MIN_FOOTER_HEIGHT` must be sized to accommodate the header row, mode row, expanded queue rows or empty-queue hint, and the multiline draft input plus frame margins. If the pane cannot fit the minimum height, the footer must hide entirely rather than clip content. Use `smart_input_visible_task_rows()` and `smart_input_queue_slot_height()` so the height calculation matches the rendered queue slot exactly; do not hardcode a full 3-row slot when fewer tasks (or zero tasks) are present. The empty-queue hint adds `SMART_INPUT_EMPTY_QUEUE_HINT_HEIGHT` to the desired height when `expanded` is true and no tasks are queued.
- **Smart Input footer content width must use the inner frame size**: `draw_smart_input_footer()` receives the outer footer size. When setting child UI min/max width inside the framed footer, subtract the horizontal frame margins (8px each side) so toolbar text, queued task rows, and draft controls cannot paint past the allocated footer width. This keeps `smart_input_queue_row_does_not_expand_past_footer_width` passing and prevents long queued prompts from hiding action buttons.
- **Queue items are left-aligned and support drag-and-drop reorder**: Queued task text must be left-aligned within the row, filling available space before action buttons. Task order is adjusted by drag-and-drop using `Sense::drag()` on each row; drop targets are shown with a green line indicator above/below the hovered row. Remove per-row Up/Down buttons when drag-and-drop is active.
- **Queued task rows must keep action buttons near the text**: Do not push Send/Edit/Delete buttons to the far right with a large flexible spacer. Use only a small fixed gap (e.g., `ui.add_space(8.0)`) after the prompt text and attachments so the buttons sit immediately next to the content. This prevents buttons from floating at the opposite edge of a wide footer and keeps the row visually compact.
- **Queue rows must cap content width so long prompts do not push action buttons off-screen**: Inside the queue `ScrollArea`, set `ui.set_max_width(queue_width)` and give the prompt label an explicit sized width that reserves space for trailing action buttons. This prevents a single long task from expanding the ScrollArea content width and hiding the buttons.
- **Smart Input queue area must use a fixed slot with a visible row background**: Do not rely on dynamic `ScrollArea` budgeting that can collapse to zero. Allocate a fixed-height slot below the mode row sized to the actual visible task count (`smart_input_visible_task_rows`), not always `SMART_INPUT_MAX_VISIBLE_TASK_ROWS`. Paint an alternating row background so the queue area is visually distinct even when a task has no text.
- **Smart Input footer height must clamp to a safe minimum so queue and draft always fit**: Dynamic footer sizing caused the queue or draft area to disappear after pane resize events. `smart_input_footer_height()` computes a `safe_min` based on current task rows (base height + queue slot + draft margin). `user_height` is respected but clamped to `safe_min..max_footer`, so the queue and draft input are never crushed.
- **Footer height is user-resizable via a drag handle**: A horizontal grip handle is drawn between the terminal output and the Smart Input footer. Dragging the handle updates `SmartInputState::user_height`, which overrides the auto-calculated height in `smart_input_footer_height()`. The handle clamps to a safe minimum that preserves queue + draft space, and to a maximum that preserves at least 3 terminal lines. Hover shows `ResizeVertical` cursor and a subtle grip visual (dots on a line).
- **Draft text area resize grip resizes the overall footer and stays anchored to the TextEdit**: The diagonal grip is positioned explicitly at the bottom-right corner of the multiline `TextEdit` rect using `ui.interact(grip_rect, ...)` so it never drifts to the far-right edge of the footer row. Dragging it updates `SmartInputState::user_height` and resets `draft_user_height` to `None`, causing the draft area to auto-fill the expanded footer. The grip clamps to the same safe minimum as the main handle so the queue area is never lost.
- **Auto-dispatch settle guard suppresses stale Idle state**: After a prompt submit, any incoming `Idle`/`TurnComplete` signal that arrives while `opencode_prompt_submit_since` is within `SMART_INPUT_AUTO_DISPATCH_SETTLE_MS` (300ms) must be suppressed by `is_stale_opencode_completion()` and discarded, not stored. This prevents a delayed previous-turn Idle from overwriting the `Working` state of the current turn, which would otherwise become eligible for dispatch after the settle window expires.
- **Stale Working recovery allows After Done to proceed when hooks stall**: OpenCode Hook/Notify Working that has not been refreshed for `OPENCODE_RUNNING_GRACE_MS * 3` (6 seconds) is cleared by `clear_opencode_stale_working_if_needed()` **only when the process is missing**. It must never synthesize Attention from elapsed time while the process is still alive.
- **Visible turn-complete recovers stale Hook Working**: `should_accept_opencode_turn_complete_chunk` blocks visible turn-complete only when Hook/Notify Working is fresh (within `OPENCODE_RUNNING_GRACE_MS`). When Working is stale, visible recovery is allowed so After Done does not stall forever.
- **Smart Input auto-dispatch clears previous delayed Enters**: `TerminalPromptSubmitOptions::smart_auto()` sets `clear_previous_delayed_enters: true`. Before scheduling confirmation Enters for a new auto-dispatched task, `submit_prompt_to_terminal` drains any existing pending second Enters for that terminal to prevent old confirmation Enters from leaking into the new task.
- **Prompt submit tracking must cover all Smart Input dispatch paths**: `apply_opencode_transport_status` must set `opencode_prompt_submit_since` when `transport_status == Working` and `source == PromptSubmit`, so the settle guard works for both manual Steer Now and auto After Done paths.
- **Smart Input TextEdit context menus must preserve non-empty selections before secondary click collapses them**: Before rendering a Smart Input draft or edit `TextEdit`, detect `secondary_pressed`, load the current `TextEditState` selection, and store the non-empty range in `SmartInputState` (`draft_context_menu_selection_range` / `edit_context_menu_selection_range`). Use the stored effective selection for Copy and Paste in the context menu, and restore it after the menu opens so the highlight remains visible. Clear stored ranges when the menu closes or when the draft/edit state resets (enqueue, submit, save, cancel, start-edit).
- **OpenCode scroll must not expose blank leading rows left by display clears**: OpenCode's TUI often issues `ED2` (erase display) during redraws, creating blank rows in scrollback history. When Smart Input reduces the viewport and the user scrolls up manually (`opencode_manual_scroll_detached`), clamp the scroll offset to `terminal_leading_blank_rows * line_height` so the viewport never sits above the first real content row. Add regression tests for the helper and for the clamp behavior.
- **Terminal output horizontal offset must be clamped to zero after each frame**: The terminal output `ScrollArea` is vertical-only. Diagonal touchpad or horizontal wheel events can leave `state.offset.x != 0.0`, which shifts all content left and clips the first columns. After `ScrollArea` processes, clamp `offset.x` to `0.0` and store the corrected state. Add regression tests that inject a non-zero x offset and verify it is reset on the next render.
- **OpenCode question prompts are handled entirely through Smart Input**: When OpenCode emits a `question.asked` event, the injected `mergen-opencode-status.js` plugin forwards the full question payload (header, question text, options, `multiple`, `custom`, `request_id`, `session_id`) to Mergen's hook service. Mergen stores the question in `TerminalEntry::opencode_pending_question` and renders an OpenCode-style question card inside the Smart Input footer. The card supports single or multiple option selection, a custom text answer when `custom == true`, Submit/Reject buttons, and keyboard operation. The user never needs to interact with the terminal TUI to answer the question.
- **OpenCode Smart Input question keyboard navigation must remain terminal-scoped**: Store the active question row in `TerminalEntry::opencode_question_focus_index`. Plain Up/Down (and Left/Right for convenience) move the highlighted row, Enter submits the focused single-choice option or the current custom answer, Space toggles focused multi-select options, and Escape rejects the question. Keyboard routing must target only the active terminal when its question card is visible in the main area; hidden/off-main terminals must never consume Arrow/Enter/Escape for a question. While a question is pending, Smart Input draft auto-focus must not steal Arrow/Enter handling; only the question custom text input may own keyboard text focus.
- **OpenCode Smart Input question state resets with the question lifecycle**: When a new question arrives, reset selected options, custom text, and `opencode_question_focus_index` to the first row, then preselect the focused option for single-choice prompts. Clearing, submitting, rejecting, OpenCode Working/Idle transitions, or terminal exit must clear the pending question and reset selection/custom/focus state together.
- **Hook service must preserve actual event kind from the body**: `parse_status_request_from_body` extracts `event.type` (e.g. `"question.asked"`) and passes it through `record_status` as `event_kind`. The deduplication logic must still enqueue metadata-bearing attention events (`question.asked`, `permission.asked`, `plan_mode_prompt`) even when the terminal's normalized status has not changed, so repeated questions are not dropped.
- **Direct hook polling must parse question payloads**: `poll_opencode_hook_service` must check `event_kind` for `question.asked` and call `parse_opencode_question_from_raw_json` on `event.raw_json` to populate `opencode_pending_question`, just as `apply_opencode_notify_inbox_event` does for notify events.
- **Smart Input question answer delivery uses the hook answer bridge with peek+ack reliability**: Clicking Submit constructs an `OpenCodeQuestionAnswer` payload and stores it in the hook service's `pending_answers` FIFO queue (`VecDeque`). The plugin polls `GET /answer` every 500ms; the endpoint is non-destructive (peeks the front answer). The plugin feature-detects `client?.question?.reply` and `client?.question?.reject`, calls `client.question.reply({ requestID, answers })` for normal answers or `client.question.reject({ requestID })` for rejected answers, and only after successful delivery calls `POST /answer/ack` to remove the answer from the queue. Failed deliveries leave the answer on the queue for retry on the next poll.
- **Auto-dispatch pauses while a question is pending**: `smart_input_auto_dispatch_ready()` returns `false` when `opencode_pending_question` is `Some(...)`. Queued After Done tasks remain in the queue until the user answers or rejects the question and OpenCode transitions back to Working.
- **Kimi thought-loop guard blocks auto-dispatch only**: When `loop_protection_enabled` is on and the active build model is Kimi-family, Mergen samples the OpenCode terminal snapshot while Working, detects repetitive thought text via `opencode_thinking_guard`, and sets `opencode_thought_loop_blocked`. `smart_input_auto_dispatch_ready_for_terminal()` then returns `false` until the pattern clears or a new prompt submit resets the guard. Manual **Send Now** is never blocked. `opencode_loop_limit_emitted` also blocks auto-dispatch.
- **Question state is cleared on status transitions and terminal exit**: `apply_opencode_transport_status` clears `opencode_pending_question` (and resets selection/custom buffers) when OpenCode transitions to `Working` or `Idle`, and `clear_opencode_state` does the same when the terminal session ends. This prevents stale question UI from lingering after the turn is resolved.
